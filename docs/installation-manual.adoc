How to get nightjar's jars into a Gradle or Maven build.

Artifacts are published to *Maven Central* — the primary route, needing no
credentials and no extra repository declaration. Every release is also pushed to
*GitHub Packages* and attached to the
https://github.com/lorands/nightjar/releases[GitHub release].

The group id is `{group}` and every module shares one version. Substitute the
current version — shown by the Maven Central badge in the README — wherever this
manual writes `{v}`.

[NOTE]
.Group id versus package name
====
The Maven group id is `{group}`; the Kotlin packages are `dev.nightjar.*`. That
is deliberate and legal — a package name and a Maven coordinate are independent
— so your imports read `dev.nightjar.domainevent.DomainEventBus` while your
build file says `{group}:domain-event`.

Releases up to 0.1.2 predate Maven Central and used the group id `dev.nightjar`.
They exist only in GitHub Packages.
====

== Which modules do you need

[cols="2,4,1"]
|===
| Artifact | Purpose | Runtime deps

| `domain-event`
| Domain events with a transactional outbox. The core; everything else builds on it
| none

| `domain-event-jdbc`
| Outbox persistence over plain JDBC. Brings `domain-event`
| none

| `domain-event-rabbitmq`
| RabbitMQ transport. Brings `domain-event`
| `amqp-client`

| `coordination`
| Process lock, worker pool, scheduler
| none

| `coordination-jdbc`
| Database-backed coordination. Brings `coordination` and `domain-event-jdbc`
| none

| `migrations`
| Schema-manifest convention + data-migration engine
| none

| `migrations-jdbc`
| Data-migration queues over JDBC. Brings `migrations` and `domain-event-jdbc`
| none

| `migrations-liquibase`
| Deploy-time schema execution. Use in an init container or CLI, never at runtime
| `liquibase-core`

| `nightjar-spring-boot-starter`
| Auto-configuration for everything above
| Spring Boot
|===

Dependencies are declared `api`, so the `-jdbc` modules pull their cores in
transitively — depend on `coordination-jdbc` and you get `coordination`,
`domain-event-jdbc` and `domain-event` too.

On Spring Boot, take the starter alone and add `domain-event-rabbitmq` or
`migrations-liquibase` only if you want those (the starter treats both as
optional and auto-configures them when present).

== Maven Central

Nothing to configure beyond the dependency itself: `mavenCentral()` is already
in essentially every build, and Maven uses Central by default.

=== Gradle (Kotlin DSL)

[source,kotlin,subs="attributes+"]
----
repositories {
    mavenCentral()
}

dependencies {
    implementation("{group}:domain-event:{v}")
    implementation("{group}:domain-event-jdbc:{v}")
}
----

=== Gradle (Groovy DSL)

[source,groovy,subs="attributes+"]
----
repositories {
    mavenCentral()
}

dependencies {
    implementation '{group}:domain-event:{v}'
    implementation '{group}:domain-event-jdbc:{v}'
}
----

=== Gradle version catalog

.gradle/libs.versions.toml
[source,toml,subs="attributes+"]
----
[versions]
nightjar = "{v}"

[libraries]
nightjar-domain-event = { module = "{group}:domain-event", version.ref = "nightjar" }
nightjar-domain-event-jdbc = { module = "{group}:domain-event-jdbc", version.ref = "nightjar" }
nightjar-coordination-jdbc = { module = "{group}:coordination-jdbc", version.ref = "nightjar" }
nightjar-spring-boot-starter = { module = "{group}:nightjar-spring-boot-starter", version.ref = "nightjar" }
----

Then `implementation(libs.nightjar.domain.event)` and friends.

=== Maven

[source,xml,subs="attributes+"]
----
<dependency>
  <groupId>{group}</groupId>
  <artifactId>domain-event</artifactId>
  <version>{v}</version>
</dependency>
<dependency>
  <groupId>{group}</groupId>
  <artifactId>domain-event-jdbc</artifactId>
  <version>{v}</version>
</dependency>
----

=== Verifying signatures

Every artifact is signed. To check one by hand:

[source,bash,subs="attributes+"]
----
gpg --verify domain-event-{v}.jar.asc domain-event-{v}.jar
----

Gradle can enforce this for the whole build with dependency verification
(`gradle/verification-metadata.xml`); see the Gradle documentation on verifying
dependencies.

== GitHub Packages

An alternative to Central, carrying the same artifacts. There is rarely a reason
to prefer it — Central needs no credentials and this does.

[WARNING]
.GitHub Packages requires a token even to read
====
GitHub's Maven registry authenticates *every* request, including reads of
packages in a public repository. There is no anonymous access and no way for the
publisher to enable it.

This surprises people because GitHub's registries do not behave alike: public
images pull anonymously from the *container* registry (`ghcr.io`), so the
reasonable assumption is that a public Maven package behaves the same way. It
does not. An unauthenticated request for a package that exists returns
`401 Unauthorized`, exactly like one for a package that does not.
====

Create a https://github.com/settings/tokens[personal access token (classic)]
with the *`read:packages`* scope.

.build.gradle.kts
[source,kotlin,subs="attributes+"]
----
repositories {
    mavenCentral()
    maven {
        name = "nightjar"
        url = uri("https://maven.pkg.github.com/{repo}")
        credentials {
            username = providers.gradleProperty("gpr.user").get()   // <1>
            password = providers.gradleProperty("gpr.token").get()
        }
    }
}
----
<1> Read from `~/.gradle/gradle.properties`, never from a file in the repository.

.~/.gradle/gradle.properties
[source,properties]
----
gpr.user=your-github-username
gpr.token=ghp_your_token_with_read_packages
----

For Maven, the repository and a matching `<server>` entry are linked by id, and
credentials never live in the POM:

.~/.m2/settings.xml
[source,xml]
----
<settings>
  <servers>
    <server>
      <id>nightjar</id>                                <!--1-->
      <username>your-github-username</username>
      <password>ghp_your_token_with_read_packages</password>
    </server>
  </servers>
</settings>
----
<1> Must match the `<repository><id>` in your POM exactly. Maven links them by
id and makes an anonymous request — which fails — when they differ.

.pom.xml
[source,xml,subs="attributes+"]
----
<repositories>
  <repository>
    <id>nightjar</id>
    <url>https://maven.pkg.github.com/{repo}</url>
    <snapshots><enabled>false</enabled></snapshots>     <!--1-->
  </repository>
</repositories>
----
<1> Only tagged releases are published; there are no snapshots in the registry.

=== Credentials from the environment

Gradle maps `ORG_GRADLE_PROJECT_<name>` onto the Gradle property `<name>`, which
suits CI better than a properties file. With a named repository you can use
Gradle's built-in credential handling and put nothing in the build file:

[source,kotlin,subs="attributes+"]
----
maven {
    name = "nightjar"                                  // <1>
    url = uri("https://maven.pkg.github.com/{repo}")
    credentials(PasswordCredentials::class)
}
----
<1> The name selects the property pair: `nightjarUsername` / `nightjarPassword`,
    supplied in CI as `ORG_GRADLE_PROJECT_nightjarUsername` and
    `ORG_GRADLE_PROJECT_nightjarPassword`.

Gradle resolves these lazily, so a build that never touches the repository never
demands them, and a missing one fails naming the property rather than with an
HTTP error.

[IMPORTANT]
.GitHub Actions, from a different repository
====
A workflow's automatic `GITHUB_TOKEN` can only read packages belonging to *its
own* repository. Consuming nightjar from GitHub Packages elsewhere needs either
a personal access token stored as a repository secret, or the package owner
granting that repository access under the package's *Manage Actions access*
settings. Neither in place produces a bare `401`, not a permissions message.

Using Maven Central sidesteps this entirely.
====

== Release assets, air-gapped builds and mirrors

Every release attaches `nightjar-<version>-maven-repo.zip` — a complete Maven
repository with POMs, jars, sources jars, javadoc jars, signatures and
checksums. Downloading it needs no account.

[source,bash,subs="attributes+"]
----
curl -LO https://github.com/{repo}/releases/download/v{v}/nightjar-{v}-maven-repo.zip
unzip nightjar-{v}-maven-repo.zip -d ~/nightjar-repo
----

Gradle:

[source,kotlin]
----
repositories {
    mavenCentral()
    maven { url = uri("file://${System.getProperty("user.home")}/nightjar-repo") }
}
----

Maven:

[source,xml]
----
<repository>
  <id>nightjar-local</id>
  <url>file://${user.home}/nightjar-repo</url>
</repository>
----

Transitive resolution behaves exactly as it does from a remote repository. This
is the route for air-gapped builds and internal mirrors: unpack the zip into a
Nexus or Artifactory hosted repository and nightjar resolves like any other
dependency, for everyone.

== Building from source

[source,bash,subs="attributes+"]
----
git clone https://github.com/{repo}.git && cd nightjar
./gradlew publishToMavenLocal
----

Installs every module into `~/.m2/repository` as `0.1.0-SNAPSHOT`. Add
`mavenLocal()` in Gradle; Maven finds it without configuration. Pass
`-Pversion=<x.y.z>` to install under a specific version instead.

[[troubleshooting]]
== Troubleshooting

`Could not find {group}:...` *from Maven Central*::
The version may not have propagated yet — Central's own indexes update within
minutes of publication, but search and third-party mirrors can lag by a couple
of hours. Check
https://central.sonatype.com/search?namespace={group}[the namespace listing] for
what is actually published.

`Could not find {group}:...` *generally*::
Check the group id: releases up to 0.1.2 used `dev.nightjar` and were never on
Central. Also confirm `mavenCentral()` is present and that Gradle's
`dependencyResolutionManagement` in `settings.gradle.kts` is not overriding
project repositories.

`401 Unauthorized` *from GitHub Packages*::
No credentials reached the registry, or the token lacks `read:packages`. GitHub
returns 401 rather than 404 for artifacts that do not exist, so this is also
what a wrong version or artifact id looks like. Check the token scope first,
then the coordinates.

Maven ignores the GitHub Packages credentials::
The `<server><id>` and `<repository><id>` do not match.

Signature verification fails::
Import the signing key from a public keyserver first
(`gpg --keyserver keyserver.ubuntu.com --recv-keys <key-id>`); the key id is in
the `.asc` file's output when verification runs without it.
